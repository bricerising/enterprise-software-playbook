— architecture atlas

The codebase as an architect sees it: who uses it, how its components depend on each other, where data is owned, what runs in the background, how it holds up when a dependency fails, and what any one change or journey touches.

Verified findings

—

Each finding was confirmed by reading the source. Reach counts the journeys whose call path runs through the code where the fix goes. Severity is how bad it is when it happens; reach is how often people pass through it. When they disagree, both matter.

    Event flow

    Which component publishes each event, and what its listeners go on to touch. Pub/sub events reach every instance but are usually not stored, so an event published while listeners are down can be lost. In-process events never leave the instance that published them.

    Background job cadence

    How often each scheduled job runs, on a log scale. Several jobs can also be woken early by an event. Hover a job for what it does and what it calls.

    Background pressure on each system

    Job runs per hour whose call path can reach each external system. It is an upper bound: a run only calls out when it finds work.

    How this was measured

    A static walk of the code, using the type checker where the stack has one, resolved every call from each entry point (HTTP routes, WebSocket actions, scheduled jobs, queue consumers) down to database queries and third-party SDK or HTTP calls, including hops through events. Components group source folders; layers run entry, middleware, domain, shared, events, platform, foundation. Middleware chains come from the framework's app, router and route registrations. Practice checks come from code patterns near each call and the findings were reviewed against the source, so read them as strong evidence rather than proof. Static analysis shows what can run, not how often it does.
